# Time Tracker — V1 Specification

Nov 4, 2026 · @Bruno

## Overview

A self-hosted, single-tenant time tracker inspired by Toggl Track. V1 is a web app; V2 adds a Windows desktop client with a tray timer and offline support. V1 must be designed so V2 needs no breaking API or schema changes.

**V1 scope (web)**

- Start/stop timer, one running timer per user
- Manual time entries (create, edit, delete)
- Projects (create, rename, recolor, archive)
- Entry list grouped by day with daily totals
- Public API with personal access tokens (PATs) for programmatic access (scripts, agents, integrations)

**V2 scope (Windows desktop)**

- Tray icon showing the running timer, with start/stop
- Offline operation with later sync

**Non-goals (V1)**

- Reports, charts, exports
- Tags, clients, billable rates
- Teams, workspaces, sharing
- Keyboard shortcuts, idle detection, integrations
- Linux/macOS desktop clients

## Tech stack and architecture

One Go API is the single source of truth. Web (V1) and desktop (V2) are both clients of the same OpenAPI contract; neither talks to the database directly.

| Layer | Choice | Rationale |
| --- | --- | --- |
| API | Go, OpenAPI-first (spec is the source of truth; server stubs and TS client generated) | Single binary, small container, same as brinketask |
| Database | PostgreSQL with `btree_gist` | Exclusion constraint enforces no-overlap at the DB level; SQLite cannot |
| Web client | React + TypeScript SPA | Live timer and inline editing; reused by desktop client |
| Auth | OIDC (authorization code + PKCE) against Pocket ID | Existing identity provider; registered users only. Personal access tokens for non-interactive clients |
| Deployment | Docker containers (API + static web), behind existing reverse proxy | Matches existing self-hosting setup |
| Desktop (V2) | Tauri v2 wrapping the same React app, Windows only | Native tray, small binaries, minimal Rust code |

**Rules**

- All timestamps stored and transported as UTC (RFC 3339). Conversion to local time happens only for display and day grouping.
- The server never trusts client clocks for the *running* timer's start when started online; it uses server time. Offline-created entries (V2) carry client timestamps and are validated on sync.
- Database migrations are versioned and run at startup or via an explicit migrate command; no ORM auto-migration.

## Data model

Three tables. Integrity rules (single running timer, no overlaps, mandatory project) are enforced by PostgreSQL constraints, not only by application code, so concurrent requests cannot violate them.

Ids are UUIDv7 and may be generated by the client. This costs nothing in V1 and is what makes V2 offline creation and idempotent sync possible. Rows are soft-deleted (`deleted_at`) so deletions can be synced to offline clients.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE users (
  id            uuid PRIMARY KEY,
  oidc_issuer   text NOT NULL,
  oidc_subject  text NOT NULL,
  email         text,
  display_name  text,
  timezone      text,  -- IANA name; NULL until set from the browser on first login (UTC used meanwhile)
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (oidc_issuer, oidc_subject)
);

CREATE TABLE projects (
  id          uuid PRIMARY KEY,
  user_id     uuid NOT NULL REFERENCES users(id),
  name        text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 100),
  color       text NOT NULL CHECK (color ~ '^#[0-9a-f]{6}$'),
  archived    boolean NOT NULL DEFAULT false,
  version     integer NOT NULL DEFAULT 1,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  deleted_at  timestamptz
);
CREATE UNIQUE INDEX projects_name_uq
  ON projects (user_id, lower(btrim(name))) WHERE deleted_at IS NULL;

CREATE TABLE time_entries (
  id           uuid PRIMARY KEY,
  user_id      uuid NOT NULL REFERENCES users(id),
  project_id   uuid NOT NULL REFERENCES projects(id),
  description  text NOT NULL DEFAULT '' CHECK (length(description) <= 1000),
  start_at     timestamptz NOT NULL,
  end_at       timestamptz,               -- NULL = running
  version      integer NOT NULL DEFAULT 1,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz,
  CHECK (end_at IS NULL OR end_at > start_at),
  -- No overlaps; a running entry occupies [start, infinity)
  EXCLUDE USING gist (
    user_id WITH =,
    tstzrange(start_at, coalesce(end_at, 'infinity'::timestamptz), '[)') WITH &&
  ) WHERE (deleted_at IS NULL)
);
-- Redundant with the exclusion (two running entries always overlap),
-- kept so the API can return a specific "timer already running" error
CREATE UNIQUE INDEX one_running_timer
  ON time_entries (user_id) WHERE end_at IS NULL AND deleted_at IS NULL;
CREATE INDEX time_entries_user_start ON time_entries (user_id, start_at DESC);
```

Notes:

- Ranges are half-open `[start, end)`, so back-to-back entries (one ends 10:00, next starts 10:00) are valid.
- Duration is always computed as `end_at - start_at`; it is never stored.
- `project_id` must belong to the same `user_id`; enforced in the API (or with a composite FK `(project_id, user_id)` if preferred).

### Personal access tokens

```sql
CREATE TABLE api_tokens (
  id            uuid PRIMARY KEY,
  user_id       uuid NOT NULL REFERENCES users(id),
  name          text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 100),
  token_prefix  text NOT NULL UNIQUE,   -- first 8 chars after 'tt_', shown in UI
  token_hash    bytea NOT NULL UNIQUE,  -- SHA-256 of the full token
  scopes        text[] NOT NULL
                CHECK (cardinality(scopes) > 0 AND scopes <@ ARRAY['read','write']),
  expires_at    timestamptz,            -- NULL = no expiry
  last_used_at  timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  revoked_at    timestamptz
);
CREATE INDEX api_tokens_user ON api_tokens (user_id);
```

- Token format: `tt_` + 32 bytes from a CSPRNG, base62-encoded. The plaintext is returned once at creation and never stored.
- A plain SHA-256 hash is sufficient (no bcrypt/argon2) because the token has 256 bits of entropy; lookup is by hash, comparison in constant time.

## Business rules

**Timer**

1. Starting a timer requires a non-archived project. Description is optional.
2. Starting while another timer runs stops the running one at the new start time, in the same transaction. The API returns both entries.
3. Online start/stop use server time. The client may send an explicit `start_at` only when editing the running entry.
4. Stopping sets `end_at = now()`. If the entry would last less than 1 second, it is discarded and the API returns 204.
5. The running entry can be edited (description, project, start time) without stopping it. Its new start must not overlap the previous entry.

**Manual entries**

1. Must have project, start and end. End must be after start.
2. Rejected if they overlap any non-deleted entry of the same user, including the running one (which occupies start → infinity).
3. Entries may cross midnight. They are listed under the day of their start in the user's timezone; their whole duration counts toward the start day. There is no maximum entry duration in V1.
4. Entries in the future are rejected (`start_at` and `end_at` ≤ server now + 1 min tolerance).

**Projects**

1. Name unique per user, case-insensitive, trimmed.
2. Archived projects keep their entries and appear in history, but cannot be picked for new entries or timers.
3. A project with entries cannot be hard-deleted; delete = soft delete, only allowed when it has no non-deleted entries. Otherwise archive it.

**Personal access tokens**

1. Scopes: `read` (all GET endpoints) and `write` (all mutations). `write` implies `read`.
2. Tokens can only be created, listed and revoked from an interactive OIDC session. A PAT can never manage PATs, so a leaked token cannot mint or extend others.
3. Expiry chosen at creation: 30, 90 (default), 365 days or never.
4. Revocation is immediate and permanent; a revoked token is never reactivated.
5. `last_used_at` is updated at most once per minute per token, to avoid a write on every request.
6. Maximum 20 active tokens per user.
7. A PAT acts as its user with exactly the same data rules; it grants no extra permissions.

**Errors the UI must handle explicitly**

| Code | When |
| --- | --- |
| `overlap` | Entry overlaps another; response includes the conflicting entry id and range |
| `timer_running` | Second running entry (should not happen via normal start, which auto-stops) |
| `project_archived` | Archived project used for a new entry or timer |
| `project_not_found` | Project missing, deleted or owned by another user |
| `invalid_range` | End ≤ start, or entry in the future |
| `version_conflict` | Optimistic concurrency failure (see API) |

## API

REST + JSON under `/api/v1`, defined in `openapi.yaml` first. Errors use RFC 9457 problem details with a machine-readable `code` from the table above.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/me` | Current user, incl. timezone |
| PATCH | `/me` | Update timezone |
| GET | `/timer` | Running entry, or 204 if none |
| POST | `/timer/start` | Body: `id?`, `project_id`, `description?`. Auto-stops running entry |
| POST | `/timer/stop` | Stops running entry |
| GET | `/entries?from=&to=` | Entries whose start falls in range (RFC 3339), newest first, paginated |
| POST | `/entries` | Create manual entry (client may supply `id`) |
| PATCH | `/entries/{id}` | Partial update |
| DELETE | `/entries/{id}` | Soft delete |
| GET | `/projects?include_archived=` | List projects |
| POST | `/projects` | Create (client may supply `id`) |
| PATCH | `/projects/{id}` | Rename, recolor, archive/unarchive |
| DELETE | `/projects/{id}` | Soft delete if no entries |
| GET | `/sync?since=` | V2: changes (incl. tombstones) since a cursor. Can be implemented in V1 at low cost |

**Concurrency and offline-readiness (required in V1)**

- Every mutable resource returns `updated_at` and an integer `version`. `PATCH`/`DELETE` require `If-Match: <version>`; mismatch → 412 `version_conflict`. Add a `version int NOT NULL DEFAULT 1` column to `projects` and `time_entries`.
- `POST` with a client-supplied `id` is idempotent: repeating it with the same body returns the existing resource (200) instead of failing. This is what lets an offline client retry safely.
- Auth: the SPA uses OIDC authorization code + PKCE; the API validates access tokens (JWT, issuer + audience + JWKS from Pocket ID). The API stores no passwords. The desktop app (V2) uses the same flow with a loopback redirect.

**Programmatic access**

The API is a public, stable contract: breaking changes only under a new `/api/v2` prefix. The same endpoints serve the web app, the desktop app and PAT clients.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/tokens` | List own tokens (name, prefix, scopes, expiry, last use). OIDC only |
| POST | `/tokens` | Body: `name`, `scopes`, `expires_in_days?`. Returns the plaintext token once. OIDC only |
| DELETE | `/tokens/{id}` | Revoke. OIDC only |

- Both credentials use `Authorization: Bearer`. A value starting with `tt_` is checked as a PAT; anything else is validated as an OIDC JWT.
- OpenAPI declares two security schemes (`oidc`, `pat`) and the required scope per operation, so the generated docs show what each token can call.
- Responses: invalid, expired or revoked token → 401; valid token without the needed scope → 403 `insufficient_scope`; PAT used on `/tokens` → 403 `oidc_required`.
- Rate limit per token (e.g. 120 requests/min) with `429` and `Retry-After`.

**Daily totals** are computed server-side or client-side from entries; there is no totals endpoint in V1. Grouping uses `users.timezone`, not the browser's timezone.

## Web UI (V1)

Single main screen modelled on Toggl's timer page, plus a projects page. Responsive enough to use on a phone browser.

**Timer bar (top, always visible)**

- Description input, project picker (required, shows color), elapsed time `HH:MM:SS`, start/stop button.
- Elapsed time is computed from the server's `start_at` and ticks locally; it re-syncs on focus and on reconnect, so a closed tab never loses time.
- Starting without a project is blocked in the UI (button disabled) before reaching the API.

**Entry list (below)**

- Grouped by day (user timezone), newest first, with the day's total.
- Each row: description, project chip, start–end, duration. Inline edit of description, project, start and end; delete with undo toast.
- "Continue" action on a row starts a new timer with the same description and project.
- Manual entry form: project, description, date, start, end.
- Overlap errors show which entry conflicts and highlight it in the list.
- Infinite scroll or "load more" by week.

**Projects page**

- List with color, name, archived toggle; create, rename, recolor, archive.

**Settings → API tokens**

- List: name, prefix (`tt_abcd1234…`), scopes, expiry, last used. Revoke with confirmation.
- Create: name, scopes, expiry. The token is shown once with a copy button and a clear warning that it cannot be shown again.

**General**

- English UI. Light and dark theme following the system.
- Durations shown as `H:MM:SS`; times in 24 h format.

## Desktop app (V2, Windows)

Tauri v2 shell around the same React app, with a local store and a sync engine. Not built in V1, but V1 must already provide client-generated ids, versions, idempotent creates and `/sync`.

**Tray**

- Tray icon reflects state (idle / running) and the tooltip shows elapsed time and project.
- Tray menu: start last project, stop, open window, quit.
- Closing the window minimizes to tray; the timer keeps running.

**Offline model**

- Local SQLite holds a copy of projects and recent entries, plus an outbox of pending mutations.
- All writes go to the local store first and are queued; the outbox is flushed in order when online.
- Pull via `GET /sync?since=<cursor>` to receive server changes, including tombstones.
- Offline timestamps come from the client clock. On every online request, the app records clock skew from the server's `Date` header and warns if it exceeds 1 minute.

**Conflicts (the hard part)**

The no-overlap rule means offline work can be valid locally and rejected on sync. Typical case: a timer runs on the web while the desktop, offline, records an entry for the same period. The sync engine must never resolve this silently.

- A rejected outbox item (`overlap`, `version_conflict`, `project_archived`) moves to a *Conflicts* list in the app with both versions shown.
- The user picks: keep local (adjusting times), keep server, or discard local.
- Two running timers (web online + desktop offline) resolve as an overlap conflict on the second one to sync.

This behaviour must be specified and tested before V2 is implemented; it is where most sync bugs will come from.

## Testing and deployment

- Integration tests against a real PostgreSQL (e.g. testcontainers), not mocks: the constraints are the core logic.
- Mandatory test cases: concurrent double start, overlap with running entry, back-to-back entries, midnight crossing, archived project, idempotent POST retry, PAT scope enforcement, expired and revoked PATs, PAT rejected on token endpoints, `If-Match` mismatch.
- OpenAPI contract tests: generated client and server must stay in sync; CI fails on drift.
- Deployment: API container + static web assets (served by the API or a separate container), PostgreSQL, configuration via environment variables (DB URL, OIDC issuer, client id, audience).
